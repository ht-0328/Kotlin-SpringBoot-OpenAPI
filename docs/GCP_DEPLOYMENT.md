# GCP デプロイメント戦略

このプロジェクトでは、Google Cloud Platform (GCP) へのデプロイに関して、ベストプラクティスとセキュリティ（最小権限の原則）に基づき、ワークフローを役割ごとに分離しています。

## ワークフローの役割

デプロイメントプロセスは以下の3つのフェーズ（GitHub Actions ワークフロー）に分かれています。

### 1. Bootstrap (`bootstrap-gcp.yml`)
- **概要**: GCP環境の初期構築を行います。
- **実行タイミング**: プロジェクト開始時や新しい環境のセットアップ時など、必要なときに **手動実行 (`workflow_dispatch`)** します。
- **処理内容**:
  - 必要な GCP API の有効化
  - Artifact Registry の作成
  - GCS バケットの作成
  - Cloud Build 用サービスアカウント (`cloud-build-builder`) の作成
  - Cloud Run Job 実行用サービスアカウント (`crypto-autotrading-lab-runner`) の作成
  - デプロイ用サービスアカウントへの最小限の IAM 権限付与
- **特徴**: リソースが存在しない場合のみ作成し、作成後は反映を待機（リトライ）する処理が含まれています。権限不足などで失敗した場合は、エラーを無視せず明示的に失敗させます。

### 2. Deploy (`deploy-gcp.yml`)
- **概要**: アプリケーションの通常デプロイを行います。
- **実行タイミング**: `main` ブランチへのプッシュ時、または手動実行。
- **処理内容**:
  - GCP 認証
  - 既存リソース（Artifact Registry, サービスアカウント等）の存在確認
  - Docker イメージのビルド
  - Artifact Registry へのプッシュ
  - Cloud Run Job の更新・作成（デプロイ）
- **特徴**: 新規リソースの作成や API の有効化、IAM の変更は **一切行いません**。必要なリソースが存在しない場合はエラーとなり、事前に `bootstrap-gcp.yml` の実行を促します。

### 3. Cleanup (`cleanup-gcp.yml`)
- **概要**: 不要になったリソースの整理・削除を行います。
- **実行タイミング**: 環境のクリーンアップが必要なときに **手動実行** します。
- **処理内容**:
  - Cloud Run Job などのリソースの削除
- **注意**: サービスアカウントの削除は自動化していません。削除済みサービスアカウントの IAM バインディングが `deleted:serviceAccount...` として残る問題を防ぐため、慎重に手動で行う方針としています。

## なぜ初期構築と通常デプロイを分けるのか

インフラストラクチャのライフサイクルと、アプリケーションコードのライフサイクルは異なります。
インフラリソース（API有効化、Registry作成など）は一度作成すればよく、日々のデプロイ（コードの変更反映）ごとにチェックや作成を試みるのは非効率です。これらを分離することで、通常デプロイの速度と安定性が向上します。

## 最小権限の原則（なぜ通常デプロイ用の権限を弱くするのか）

セキュリティの観点から、GitHub Actions（CI/CD環境）に付与する権限は必要最小限に留めるべきです。

- **初期構築時（Bootstrap）** は、リソースを作成するために一時的に強い権限（`roles/iam.serviceAccountAdmin`, `roles/artifactregistry.admin` など）が必要になります。初回実行時に成功したり失敗したりした原因は、作成直後の IAM 権限やリソースの反映に時間がかかる（反映待ち不足）可能性が高いです。
- **通常デプロイ時（Deploy）** の `github-actions-deployer` は、以下の **最小権限** で動作するように構成しています：
  - `roles/cloudbuild.builds.editor`
  - `roles/run.developer`
  - `roles/serviceusage.serviceUsageConsumer`
  - 対象サービスアカウント（`cloud-build-builder`, `crypto-autotrading-lab-runner`）に対してのみ付与される `roles/iam.serviceAccountUser`（プロジェクト全体ではなく、サービスアカウント単位で付与）

これにより、万が一デプロイ用の認証情報が漏洩した場合でも、インフラストラクチャ全体への被害を最小限に抑えることができます。

## 運用上の注意（Phase1）

現在は **Phase1（シミュレーション運用）** の段階です。
本システムは実際の注文（実注文）を行う設定にはなっておらず、あくまでシミュレーション用の構成です。実注文を行う設定には変更しないでください。
既存の `strategy_name` 入力から `APP_TRADING_STRATEGY_NAME` 環境変数へのマッピング機能は維持されており、シミュレーション戦略の切り替えに使用されます。
